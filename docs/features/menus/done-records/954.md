# Done Record

- **Milestone / PR:** A venue's library holds a dish once — PR #954 (retrospective)
- **Head commit this record describes:** `9d29fe89813b0bbeba79015e47e8636556351704` (the merge commit; already deployed to dev before this record existed)
- **Author:** Claude Opus 5 on behalf of Jeremy Miedreich

**This record is retrospective**, for the same reason as #951's — see that record's closing note. It is written after the fact against the actual merged diff and the actual dev deployment result.

**This PR carries a destructive migration.** The owner was told explicitly, before merge, that deploying it would merge duplicate library items in the dev database and delete the losing rows, and gave the go-ahead knowing that. Recording it here as well because a destructive migration is exactly the kind of change this checklist exists to slow down for.

Paths known but not attacked, as UNTESTED:

- **The builder's "create as new" reuse path has no automated test in this PR**, unlike the import path. It was read and reasoned about, and the UI suite's overall pass count is consistent with it working, but no test names it directly. Residual risk: a regression here would likely surface as a generic add-item failure rather than a clearly attributable one.
- **A venue with a duplicate spanning more than two items** (three or more copies of one dish) was exercised only incidentally by whatever the local database happened to contain, not by a constructed test case.
- **Concurrent imports racing to create the same new item name** — the unique index will refuse the loser, but what the operator sees when that happens (a raw constraint error vs. a friendly message) was not checked.
