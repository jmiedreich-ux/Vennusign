## Design questions

- **Does it make sense for this to be reviewed or skipped?** Rotation is not a step a person completes, so there is nothing to review. It is the consequence of assignments the operator already made and already confirmed on the assignment page.
- **Can the user edit it?** Yes, where it belongs: by assigning or unassigning pages, and by the menu's dwell. Nothing new to edit was introduced on the display, which has no input.
- **Can the user go back a step?** N/A — a rotating board has no steps. The operator's control is the assignment page.
- **Is delete needed? Is edit needed?** No. Unassigning a page is the delete, and it already exists.
- **Does it need to talk to another function?** It reads assignments and the published snapshot, both already there. It deliberately does **not** touch `PlaylistRotation`: that cycles promotional slides and hands off for menus, and folding menu pages into it would put two different clocks in one component.
- **Is every word shown to the user plain and clear?** N/A — this adds no user-facing copy. Related: the back office's existing promise, *"a screen holding more than one page rotates between them"*, is now true; it was not before.
- **Paths that should exist to make this easier in context?** One is named and not built: the operator cannot see the rotation without walking to the screen. A preview of the cycle in the builder would be the obvious affordance and is not in scope here.
- **Should this be drag-and-drop?** N/A — page order comes from the menu's own page order, which is already reorderable in the builder.

## The behaviour

- **Happy path works end to end:** PASS — two pages assigned to one screen, published, and the display payload carried both with their sections and the menu's dwell. Verified by probe against the running API, not by reading code.
- **Loading, empty, disabled, error and retry states:** PASS for empty — a screen with no assignment keeps the previous behaviour (`assignment` is null, sections unfiltered), and a one-page screen is returned unchanged. The hook is called before content arrives and copes with `undefined`, because a React hook cannot sit behind the component's early returns. Loading/error/retry belong to `DisplayPage`'s existing fetch and are untouched.
- **Validation on first entry and when editing an already-saved value:** N/A — no input is added. The rotation reads assignments that the assignment page already validates.
- **Error recovery — retry without losing what was entered:** N/A — nothing is entered on a display.
