VennueSign Mosaic V1 Blueprint Direction

A plain-language test of whether the proposed content and presentation path is truly the right place to build from—and what can safely happen in parallel.

Study date: August 30, 2026 · Evidence base: Vennusign master at 40a03e6 · Advisory only

Answer V1 outcome Bias test Alternatives Build order Blueprint coverage Parallel work Owner decisions Evidence

Yes—the content-to-presentation-to-display path is the right principal direction for Mosaic V1.

It is not right merely because Menu and Theme work came first. It is right because it is the smallest useful customer journey that tests the most important new boundaries: what the content means, how it should look, what was approved, where it should go, what the physical output received, and what is actually showing.

The path must not become one long Data Model project. Begin with the observable first-live-screen journey, settle the small set of contracts that are expensive to change, and then build a fixture-backed end-to-end skeleton while the real Core, Theme, Runtime, Connect, and support foundations proceed in parallel.

Route counts are not roadmap weight. Core has 103 candidate route groups while Runtime has 12, but Runtime delivery, recovery, and Showing State are indispensable. Connect Mapping and Control has zero primary routes, but it is still the safety boundary for imported data.

What Mosaic V1 should visibly accomplish

Plain V1 outcome: An authorized operator at one venue can create or use one Menu presentation, publish an immutable Release, assign it to one logical wall/screen, pair the correct Player Output, see that the Package is applied and showing, perform an immediate 86 without publishing, keep the last valid display through a failure, roll back safely, and use support evidence to tell desired state from actual state.

The first acceptance journey can deliberately be small: one organization, one venue, one wall of one screen, one Player Output, one content type, and a basic or fixed Theme. The underlying contracts must still be multi-venue safe and prove cross-organization and cross-venue refusal.

This is a supportable release, not just a demo. “Published” must never be treated as “showing.”

Did current Menu work bias the choice?

Yes, the bias is real

  • Menus has the deepest accepted behavior and feature records.
  • Theme Studio has received substantial design attention.
  • The renewal was discovered through Menu-shaped limits.
  • Core owns 103 of 156 route groups; Content and Design owns 35.
  • Tests and acceptance work are concentrated in Menu, Screens, pairing, and display.

Why the path still wins

  • It creates visible customer value.
  • It crosses Core, Runtime, and minimum Platform truth.
  • Menu already exercises nested content, placement values, imports, publishing, 86, rollback, assignment, rendering, and offline behavior.
  • It reuses the strongest foundations while exposing the largest missing contracts.

The bias control is to treat Menu as the first adapter—not the universal schema. Use a non-customer-facing cinema/showtimes fixture to challenge field, collection, source, and query assumptions. Do not require a complete second product in V1.

Recommended way to begin

Reconcile authority and define acceptance. Resolve stale records and claims, decide the release audience, and write the exact first-live-screen journey.
Freeze the smallest shared contracts. Tenant/venue; menu.v1; Theme binding; Release versus Package; Screen/Wall versus Player Output; desired versus actual evidence; Connect authority.
Build an executable walking skeleton. Use frozen neutral fixtures or an explicitly disposable adapter to prove Release → assignment → authenticated Output → Package → Showing → recovery → support evidence.
Build the real foundations in parallel. Core model/content, Theme compatibility, Runtime identity/evidence, Connect provenance, Platform read support, auth sufficiency, and characterization.
Replace every disposable adapter. Integrate real Presentation, Release, Package, overrides, recovery, and evidence without a second source of truth.
Prove Mosaic. Test cross-tenant refusal, publish/rollback, 86, authenticated delivery, offline continuity, reconciliation, showing evidence, and support diagnosis.
Strongest objection: a walking skeleton could freeze today's Menu payload into the new Runtime contract. It is safe only if the fixture or adapter is versioned, disposable, has a deletion condition, and cannot become a second truth. Production Package schemas wait for minimum menu.v1 and Theme-binding semantics. If those controls cannot be enforced, complete the minimum model/compiler first.

Customer needs versus architecture convenience

Customer V1 needs

  • safe identity and venue context;
  • one useful content and presentation path;
  • publish, Release, rollback, and 86;
  • logical assignment and secure physical delivery;
  • cache, recovery, and showing evidence;
  • cross-tenant refusal and support visibility.

Not reasons to expand V1

  • four separately deployed APIs;
  • whole-product cleanup;
  • all sign-in and onboarding branches;
  • full Model or Theme Studio;
  • all providers, schedules, walls, and fleet tools;
  • equal slices from every family.

Queue rule: a free coordinator is not permission to start a package whose contract gate is still blocked.

Owner decisions that can change the V1 boundary

  1. Is Mosaic a private pilot, limited production release, or general availability?
  2. Must it onboard a new customer, or may it begin with existing/seeded organizations?
  3. Must it prove physical hardware, and which player environment is authoritative?
  4. Is one output enough, or must multi-output and synchronized activation ship?
  5. Is a basic preset Theme enough, or is customer Theme authoring part of the promise?
  6. Is paste/import required? Is any live POS or showtime feed required?
  7. Must multi-venue behavior be demonstrated end to end, or structurally enforced and refusal-tested?
  8. What offline duration, rollback, recovery, and retention targets are promised?
  9. Which scheduling behavior is required beyond always-on or already reusable scheduling?
  10. What minimum support/fleet evidence is required to operate the release?
  11. Which Menu behaviors remain unchanged, and which are deliberately redesigned?
  12. What exact model, Release, Package, Theme compatibility, and Player Output contracts are approved?
  13. What migration window and adapter-retirement rule apply to existing data?
  14. Will Platform perform writes in V1, requiring full workforce authority and privileged-action audit?

These are focused reconciliation questions. They are not a reason to audit the whole product.

Appendix: all 82 named blueprint areas

This compact ledger demonstrates complete blueprint coverage. “Contract” means settle the boundary now even when full implementation is deferred.

Core — Account and Business Structure (7)
  1. Authentication: reuse and characterize; no first rebuild.
  2. Authorization: reuse/reshape for organization and venue refusal.
  3. Sessions: reuse actor/org/venue/capabilities.
  4. Onboarding: defer unless new-customer V1.
  5. Organizations: reuse; reshape only shared/effective state crossed by V1.
  6. Venues: reuse as mandatory operational boundary.
  7. Subscriptions and Billing: reuse needed entitlement; defer expansion.
Core — Content and Design (5)
  1. Data Models: build/reshape minimum immutable menu.v1.
  2. Content: reshape typed records, revisions, composition, state.
  3. Presentations: build/reshape Content plus Theme.
  4. Themes: build/reshape immutable revisions, bindings, state responses.
  5. Assets: build/reshape minimum immutable hashed assets.
Core — Display Planning (5)
  1. Screens: reuse/reshape logical lifecycle.
  2. Walls: wall-of-one now; advanced planner later.
  3. Player Administration: reshape staff claim and binding.
  4. Assignments: reshape to Release → Wall/Screen.
  5. Scheduling: reuse minimum; defer broad suite.
Core — Change Control (5)
  1. Drafts: reshape around immutable revisions.
  2. Publishing: build/reshape controlled validation and idempotency.
  3. Releases: build immutable Release, prior version, rollback.
  4. Operational Overrides: preserve immediate 86/restore.
  5. Audit: reuse/reshape meaningful action evidence.
Connect — Connections and Sources (5)
  1. Connectors: preserve current adapters; broad renewal later.
  2. Connections: contract scope; build for selected provider only.
  3. Data Sources: contract source identity.
  4. Transports: reuse selected behavior; defer expansion.

  2. Data Mappings: contract against Data Model paths.
