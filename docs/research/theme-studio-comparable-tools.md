# Comparable Tools Research: Theme Studio

**Status: early-stage exploratory design research, not a build spec.** This document surveys how eleven external tools structure theme/style editing, live preview, versioning, and (where applicable) time-of-day or variant scoping. It exists to give the Theme Studio design conversation outside reference points, not to prescribe what Theme Studio should do. Every factual claim below is cited inline to a primary source (vendor documentation, help center, source spec, or developer docs) reached via direct fetch or search-result excerpt of that same page. Where a tool's own documentation could not be found or verified after a genuine search, that is stated explicitly rather than filled in from general knowledge. Nothing here should be read as a recommendation — the closing section lists gaps as neutral open questions only.

---

## 1. Canva — Brand Kit / Brand Templates

**Structure.** A Brand Kit is a per-team hub storing "essential brand elements like logos, fonts, colors, templates, and more" ([Brand Kit Best Practices Guide](https://www.canva.com/help/brand-kit-best-practices/)). Brand Templates are separate design files that get published and then added to a Brand Kit; once added they surface in a dedicated **Brand Templates** section so team members can "find approved templates quickly" ([Manage your brand assets in Canva](https://www.canva.com/help/find-and-manage-brand-assets/)). Templates remain visible to the owner on their **Projects** page and to team members on the team's **Brand** page ([search excerpt of Canva Help Center results](https://www.canva.com/help/brand-template-locks/)). So the pattern is: design a template → **Publish** it as a Brand Template → it lists inside the Brand Kit/Brand page → someone else opens it to start a new design. This is a library → editor → publish flow, but the "editor" for the template itself is the same general Canva design canvas, not a distinct theme-specific workbench.

**Locking as scoped editability.** Rather than a semantic-selection model, Canva gives Brand Templates element-level **locks**: "Locks help maintain consistency by preventing changes to key elements in a Brand Template, such as logos, text styles, and layout components," with finer-grained options (e.g., lock position but leave text/image editable) ([Apply locks to Brand Templates](https://www.canva.com/help/brand-template-locks/)).

**Live preview / proofing.** Editing happens directly on the real canvas (WYSIWYG), not a separate proofing mode — there is no evidence in Canva's help docs of sample-dataset-driven proofing; a Brand Template is proofed by looking at the one design it contains.

**Versioning.** Two distinct mechanisms exist:
- **Design version history** (any design, not specific to Brand Templates): "You can restore an older version of your design from the File menu... You can restore up to 1,000 previous versions, with no time limit on how long versions are kept," restricted to Pro/Teams/Business/Education/Nonprofit plans and to users with edit access ([Review and restore older versions of designs](https://www.canva.com/help/version-history/)).
- **Brand Template publishing is overwrite-in-place, not immutable revisions.** Editing a design that originated from an existing Brand Template and choosing "Republish with changes" **replaces** the previous template outright: "the existing template is updated with the changes... once updated, your previous Brand Template design will be replaced" ([search excerpt of Publish designs as Brand Templates](https://www.canva.com/help/publish-team-template/); also [Design with Brand Kits and Brand Templates](https://www.canva.com/help/using-brand-templates/)). So the "save" model for the reusable template itself is closer to live-editing a single mutable object than to saving numbered, immutable revisions — the underlying design's own version history (1,000 restorable snapshots) is what provides any rollback safety net.

**Time-of-day / variant scoping.** No mention found in Canva's Brand Kit/Brand Template documentation of dayparting, scheduling, or theme variants; Canva's brand system is not aware of time or context at all.

**Gaps relative to Theme Studio (neutral, not prescriptive).** Canva conflates "the template" and "the published, shareable version of the template" into one overwritable object, whereas Theme Studio's stated model keeps saves as immutable revisions distinct from a live-editable draft — an open question is how (or whether) a Theme Studio revision history should also expose per-element lock semantics the way Canva does for Brand Templates.

## 2. Shopify — Online Store 2.0 theme architecture / theme editor

**Structure.** Shopify's flow is library → editor → publish, explicitly modeled around **draft vs. live** theme objects rather than menu-style save slots. From the **Themes** page in admin, "Your published theme has the Live status... your unpublished themes appear in the Draft themes section" ([search excerpt, Publishing themes](https://help.shopify.com/en/manual/online-store/themes/managing-themes/publishing-themes)). A merchant can "install your new theme but keep it unpublished... to rebuild your homepage and test features 'behind the scenes' without affecting your live customers," and can hold up to 20 themes total, though "only one theme can be published at a time" ([same source]). Publishing a new theme doesn't delete the old one — "your previously published theme moves to the Draft themes section, and none of your theme changes are lost."

Inside the editor itself (**Online Store > Themes > Customize**), the UI is a two-pane workbench: a left/adaptive sidebar shows "a tree view of all the content for the template that you're currently viewing," and selecting a section or block loads its settings into a settings panel; on wide windows this is a double-sidebar layout, collapsing to a single stacked sidebar on narrow windows ([Theme editor features overview](https://help.shopify.com/en/manual/online-store/themes/customizing-themes/theme-editor/features-overview)). The center of the editor shows the theme's name plus a **Live**/**Draft** status label and a mobile/desktop preview toggle ([same source]).

Under the hood, Online Store 2.0 replaced Liquid-only templates with **JSON templates**: "Every page in Shopify online store 2.0 is rendered using JSON template file(s), which lists a page's sections and stores setting data for every section added or edited" ([search excerpt synthesizing shopify.dev docs](https://shopify.dev/docs/storefronts/themes/tools/online-editor)), and sections are available on every template (not just the homepage), with app blocks letting third-party apps inject UI into a section without editing theme code.

**Semantic click-to-select.** Shopify's **preview inspector** is a close analog to Theme Studio's "semantic selection" idea: it "allows you to navigate sections and blocks directly in the preview, and makes finding corresponding settings more intuitive," drawing outlines over rendered elements using the browser's `Element.getBoundingClientRect()` and requiring theme authors to follow layout conventions (e.g. use `gap` not `padding` for spacing, avoid negative margins, disable fixed positioning during inspection) so the outlines stay accurate ([Theme editor preview inspector best practices](https://shopify.dev/docs/storefronts/themes/best-practices/editor/preview-inspector)).

**Live preview / proofing.** The editor preview is explicitly meant to be the real storefront: "the merchant should see exactly what will appear in the storefront when the theme is live" ([search excerpt, The theme editor](https://shopify.dev/docs/storefronts/themes/tools/online-editor)). This implies rendering against real store content/products rather than synthetic sample data — Shopify's docs describe live color/text updates reflecting directly in the preview but do not describe a generated-sample-dataset proofing mode.

**Versioning.** Within the editor, "Changes remain unsaved until users click the **Save** button... After you save your changes, you can no longer redo or undo" ([Theme editor features overview](https://help.shopify.com/en/manual/online-store/themes/customizing-themes/theme-editor/features-overview)) — i.e., undo/redo exists only pre-save, and there is no evidence of a numbered, restorable revision history for a merchant's own edits inside the editor. Separately, Shopify does track a theme's **version number**, but this refers only to how a theme compares to the latest release available in the Theme Store (for reviewing "release notes of a theme update"), not to a merchant's edit history ([Theme architecture versions and sources](https://help.shopify.com/en/manual/online-store/themes/managing-themes/versions)). So the draft/live duplication (keep old live theme as a draft after publishing a new one) is Shopify's practical substitute for rollback, not a formal version-history feature.

**Time-of-day / variant scoping.** No mechanism for daypart- or schedule-based theme variants was found in Shopify's theme documentation; a theme is either Live or Draft, with no time-based automatic switching between them.

**Gaps relative to Theme Studio.** Shopify's draft/live duplication (rather than immutable numbered revisions) raises an open question about how many "shadow" copies of a theme a system should let accumulate before it needs an explicit history model; its preview inspector shows one working implementation of click-an-element-to-find-its-setting, which Theme Studio's semantic-selection goal could be compared against for interaction specifics not (yet) covered in Theme Studio's design.

## 3. Squarespace — style editor

**Structure.** There is no separate template library step in the everyday workflow — a user opens the **site styles panel** via the paintbrush icon while on/editing a page, and it directly edits the live site: "Use options in site styles to change your site-wide style settings" ([Making style changes](https://support.squarespace.com/hc/en-us/articles/205815788-Making-style-changes)). The panel covers fonts, colors, buttons, forms, spacing, animations, and image layouts sitewide, plus section-specific overrides for headers, footers, blog, portfolio, and store pages ([same source]). Squarespace also ships preset **Themes** (grouped as "Professional," "Playful," "Innovative") that bulk-set fonts/colors/buttons as a starting point, which the user can still hand-adjust afterward ([same source]) — structurally the closest thing here to a "theme revision," but it is a one-time apply, not a saved/swappable object.

**Live preview / proofing.** Style changes are made directly on the real, live page content (true WYSIWYG against the actual site) — not a synthetic mock or sample dataset.

**Versioning.** Squarespace's model is deliberately session-scoped, not a persistent history: "you can click the undo and redo arrows... apply to most things you can change including blocks, sections, section styles, and site styles" while editing, but "If you click Save... you can continue to undo or redo changes. When you Exit the page, this ends your editing session, and any changes you made can't be undone or redone anymore" ([Using undo and redo in Squarespace](https://support.squarespace.com/hc/en-us/articles/4403167416461-Using-undo-and-redo-in-Squarespace)). Squarespace's own FAQ confirms there is no fallback beyond that: "Squarespace doesn't have auto-save or revision history features when editing, so content lost or deleted cannot be restored... if the browser is accidentally closed while editing" ([search excerpt, Troubleshooting lost content](https://support.squarespace.com/hc/en-us/articles/206543417-Troubleshooting-lost-content)). The only way back to a prior look after saving is to manually reset styles to defaults or reapply an earlier preset Theme.

**Time-of-day / variant scoping.** No daypart, schedule, or style-variant concept was found in Squarespace's style documentation; a site has one active style configuration at a time.

**Gaps relative to Theme Studio.** Squarespace shows a workflow where "save" is nearly instantaneous and permanent with no formal versioning safety net beyond session undo — an open question this raises for any tool with "immutable, versioned saves" as a design goal is how much friction a save step should add relative to Squarespace's near-zero-friction (but also norollback) approach.

## 4. Yodeck

**Structure: Discover Templates gallery → Layout Editor → Draft/Publish.** Templates are reached two ways: a standalone **"Discover Templates" gallery** tab on the Layouts list page, and a **Templates tab built into the Layout Editor's own left sidebar** for in-context browsing (with search, horizontal/vertical orientation filters, category browsing, and infinite scroll; templates display two-per-row inside the editor vs. multi-column on the standalone gallery) ([Using Templates in the Layout Editor](https://www.yodeck.com/docs/user-manual/layout-editor-templates/)). Applying a template to a non-empty canvas triggers a "Warning for Replacement" confirmation; an empty canvas applies immediately, and any application can be undone with Ctrl/Cmd+Z ([same source]). Enterprise accounts additionally get a distinct **Branded Templates** object type, reached under a Layouts > Branded Templates list, with per-item context-menu actions (edit, publish, duplicate, delete); opening a published one and choosing "Import Template" brings it into the Layout Editor as an editable starting layout while keeping certain elements (logos, fonts, colors) locked ([Branded Templates & Layout Design Guide](https://www.yodeck.com/docs/user-manual/branded-templates-layout-editor/)).

**Draft/Published as versioning-lite.** Branded Templates have two states: "**Draft:** Work-in-progress templates. Editable and visible only to Admins and Template Managers" and "**Published:** Finalized versions accessible to authorized users" ([same source]) — a review-gate model rather than a numbered revision history.

**Live preview / proofing.** Documentation describes a **hover-to-preview** interaction (hover a template thumbnail, click the eye icon for an enlarged preview, then "Use Template" to apply) ([Using Templates in the Layout Editor](https://www.yodeck.com/docs/user-manual/layout-editor-templates/)), which is closer to a static/generic preview of the template's own sample content than proofing against a venue's real menu data. Separately, Yodeck layouts can bind to live data sources — e.g., Google Sheets can be embedded, though "Google Sheets embeds use a fixed frame size and don't automatically resize to your screen, and content cannot reflow or adjust dynamically" ([search excerpt, Google Sheets app doc](https://www.yodeck.com/docs/user-manual/google-sheets/)) — indicating no reflow-aware, capacity-checked proofing against real content sizes.

**Time-of-day / variant scoping — the closest analog found to Theme Studio's dayparts.** Yodeck's **Schedule → Event → Content** model lets an Event assign a specific Layout, Media, or Playlist to a start/end time window, with recurrence (daily/weekly/monthly/custom), layered priority ("The Event listed higher on the right-hand side 'Events List' always takes precedence over events below it if they overlap in time"), and fallback "Filler Content" for gaps ([Schedules Introduction](https://www.yodeck.com/docs/user-manual/schedules-introduction/)). This assigns different **layouts** to different times, not a **style/theme** independent of content — Yodeck's own documentation does not describe a theme-only variant concept; it only supports swapping whole layouts by time slot.

**Gaps relative to Theme Studio.** Yodeck's Schedule/Event model achieves a dayparting-like effect only by swapping entire layouts (content + style bundled together) rather than swapping a style layer under fixed content, which is a structurally different approach from Theme Studio's separation of theme from content; its template preview is a static thumbnail/eye-icon view rather than a running proof against the venue's actual data, which is an open point of comparison against Theme Studio's "always-visible capacity gauge" idea.

## 5. Rise Vision

**Structure.** Starting point is a template gallery inside the Presentations area: "Click Presentations in the navigation bar on the left, then click + Add Presentation... browse, search, or filter to find a template you like... click + or Start with this Template" ([search excerpt of Get Started with Rise Vision in 3 Steps](https://help.risevision.com/hc/en-us/articles/115002868706-Get-Started-with-Rise-Vision-in-3-Steps)). Inside the editor, "each presentation is made of components listed on the left side of the editor... click a component to customize it... use the preview on the right to click directly on components and edit them visually" — a semantic, component-based selection model (click the actual rendered element, not an x/y box) reasonably close to Theme Studio's stated approach ([search excerpt](https://help.risevision.com/hc/en-us/sections/360004946912-Using-Templates)). A "List" component type can bind to a Google Spreadsheet for automatic content updates, or be edited manually ([same source]).

**Publish is a distinct, explicit step from editing.** "Changes are saved automatically but will not appear on Displays until the presentation is published," with the Publish control "located in the top-right corner of the editor" ([search excerpt](https://help.risevision.com/hc/en-us/categories/360001862672-Create-Edit-Presentations)) — so Rise Vision has an editor/draft state and a separate publish action, similar in shape to Shopify's/Yodeck's draft-then-publish pattern, though it is unclear from available docs whether "publish" creates a distinct, retrievable revision or simply flips a live flag.

**Optional review workflow.** Rise Vision Enterprise has a formal approval gate: "Content publishing approval lets you set up a review and approval workflow for Presentation updates before they go live on your displays." A Content Editor edits a presentation (which moves to Draft mode), then "click Send for Review" to route it to any user with the Content Publisher role, who can approve or reject; accounts can opt out entirely by giving all relevant users both roles ([Content Publishing Approval](https://help.risevision.com/hc/en-us/articles/41506732615828-Content-Publishing-Approval)).

**Live preview / proofing.** Rise Vision has a **Virtual Display**: "The Virtual Display will only show content from the Schedule you select, and any updates made to the Schedule will automatically reflect in the Virtual Display preview," letting a user "simulate how your scheduled content will appear on a screen without needing a physical display device" ([How to Preview Content on a Virtual Display](https://help.risevision.com/hc/en-us/articles/23573354366868-How-to-Preview-Content-on-a-Virtual-Display)). This previews against the actual configured Schedule/Presentation content (real content, not a synthetic mock), but it previews content+schedule together rather than a theme layer in isolation.

**Versioning.** No help-center article describing a numbered revision history, prior-version restore, or rollback for presentations was found after a genuine search of help.risevision.com; this appears to be **absent or undocumented** rather than merely unsearched — Rise Vision's own search results surfaced only unrelated "previous Chrome app version" and "unsupported content" articles. This absence is noted explicitly per the research instructions rather than assumed.

**Time-of-day / variant scoping.** Rise Vision's own **Schedules** feature is the vehicle for time-of-day control: "Schedules are the link between your Presentation and your Display, controlling which Presentation will be shown on which Displays, and when it will be shown — the day of the week and time of day" ([search excerpt](https://help.risevision.com/hc/en-us/categories/115000646826-Schedule-Your-Content)). As with Yodeck, this swaps whole Presentations (content+design together) by time, not an independent theme/style layer.

**Gaps relative to Theme Studio.** No documented version history/rollback for presentations is a notable absence to flag (not fill in); the approval-workflow model (Content Editor drafts → Content Publisher approves) is a review-gate pattern Theme Studio's current five-screen design does not appear to mention.

## 6. ScreenCloud

**Structure.** ScreenCloud Studio separates a general-purpose design tool, **Canvas** ("a simple design editor tool built into ScreenCloud Studio's CSM which can be used to create screen-ready content like menu boards and posters"), from **Channels** (the scheduling/playback object) ([ScreenCloud Studio: Canvas](https://help.screencloud.com/en/articles/10120182-screencloud-studio-canvas)). Canvas offers a **Template Gallery** of pre-built, screen-specific designs plus the ability to save any Canvas as a reusable team **Template**, with element locking so only specific content (not layout) can be edited by others, for on-brand consistency ([same source]).

Separately, ScreenCloud has a **CSS & Zone Layout** system for custom multi-zone screen layouts: zones are declared in a JSON **Config** section (IDs, names, overall canvas size) and positioned/sized via a **CSS** section (width, height, top, left, z-index, plus `is_flexible`/`is_scalable` flags for how a layout adapts to different screen aspect ratios) ([ScreenCloud CSS & Zone Layout Guide](https://help.screencloud.com/en/articles/10120826-screencloud-css-zone-layout-guide)).

**Live preview / proofing.** The zone-layout editor's preview is structural, not content-driven: "the preview panel on the right updates to show zone boundaries and dimensions... shows only the structural layout — not actual scheduled content" ([search excerpt of the CSS & Zone Layout Guide](https://help.screencloud.com/en/articles/10120826-screencloud-css-zone-layout-guide)). This is explicitly a static/placeholder mock of geometry, not real or generated sample content.

**Versioning.** Channels have a lightweight, single-step undo: "you can select the drop-down arrow on the yellow 'Publish' button to view the last update made and the option to discard any changes published. However, once content has been confirmed to go live, you can't revert or discard the changes made using the menu option and you'll have to remove the changes made manually" ([search excerpt, ScreenCloud Studio: Channels](https://help.screencloud.com/en/articles/10120125-screencloud-studio-channels)) — i.e., one level of "discard last change," not a numbered/restorable history. Note ScreenCloud's help center separately documents a "**Version History**" feature, but that refers to the ScreenCloud OS **player app's software version**, not content/design history ([search excerpt](https://help.screencloud.com/en/articles/10121205-how-to-find-the-screencloud-player-app-version-on-your-device)) — a naming overlap worth flagging so it isn't mistaken for content versioning.

**Time-of-day / variant scoping.** ScreenCloud supports time-based content control at the Channel/Playlist level: playlists can be scheduled to run at specific times and date ranges, media can carry start/expiration availability windows, and there's a distinct "Screen Operating Hours" feature for on/off scheduling — but this is documented as scheduling **which playlist/content plays when**, not a documented style/theme variant concept independent of content.

**Gaps relative to Theme Studio.** ScreenCloud's zone-layout preview being explicitly structural-only (dimensions/boundaries, not real content) is a useful negative data point against Theme Studio's "always live, real-data proofing" goal — it shows a live-preview implementation that deliberately does not attempt content-accurate proofing, which is an open point of comparison rather than a flaw to fix.

## 7. Xibo

**Structure: Layout list → Layout Editor → Checkout/Draft/Publish.** Layouts are managed from a **Layouts** page under **Design** in the CMS; opening one for editing uses a canvas-centered editor with a **Toolbox** (content types) on the left, a **Properties Panel** for the selected item, and status/duration indicators at the top ([Layout Editor Overview, search excerpt](https://account.xibosignage.com/manual/en/layouts_editor)). Templates are available "from inside the Layout Editor by clicking to open the Toolbox and selecting the Xibo Exchange button" ([search excerpt, Using Templates](https://xibosignage.com/manual/en/layouts_editor_using_templates)).

Xibo's edit-safety model is a genuine **checkout/draft/publish** pattern, structurally close to Theme Studio's "never live-edit a saved revision" goal: "When you click Checkout to create a draft of the Layout to enable editing, a copy of the Layout is made in a draft status. Xibo will continue to show the Published Layout design already in Display Schedules" while the draft is being worked on ([search excerpt, Xibo CMS - Layout Status blog](https://xibosignage.com/blog/new-layout-status)). From the draft, a user can **Discard** ("all changes will be discarded and the Layout will revert back to the previous Published version") or **Publish** ("overwrite the existing Published Layout") — and publishing itself can be immediate ("Publish Now") or scheduled for a future date/time, with an optional setting to auto-publish any draft 30 minutes after the last edit ([search excerpt, Layout Design Changes / publish options](https://account.xibosignage.com/manual/en/layouts_editor_publish_options)). Xibo's own blog frames the guarantee explicitly: "Your original version will remain untouched until you tell Xibo to overwrite it with Publish!" ([Xibo CMS - Layout Status](https://xibosignage.com/blog/new-layout-status)).

**Live preview / proofing.** Inside the editor, a **Play** button (bottom-left of canvas) or a full-screen preview icon renders the layout live; the documentation found does not specify whether this preview evaluates live data-bound widgets against real feed content or only renders static/placeholder content, so this is not fully verifiable from Xibo's own docs as searched.

**Versioning.** The checkout/draft/publish model above is Xibo's versioning mechanism, but it holds only **one previous published state** at a time (the design being replaced), not an arbitrary-depth numbered history — no evidence was found of Xibo keeping multiple prior published revisions for later rollback beyond the single most-recent one.

**Time-of-day / variant scoping — Xibo's Dayparting is the strongest direct analog found to Theme Studio's "dayparts" concept.** "Dayparting allows Displays to show relevant content based on the immediate needs of your audience" by defining named time blocks; the docs give exactly a restaurant example — "a Breakfast, Lunch and Dinner daypart, each of which starts and ends on a different day" — configured centrally under **Dayparting** in the CMS menu, with per-weekday exceptions ("Saturday and Sunday are configured with different start/end times than weekdays") ([Dayparting, search excerpt](https://account.xibosignage.com/manual/en/scheduling_dayparting)). When scheduling an event, selecting a Daypart swaps the time pickers to date-only pickers and derives start/end times from the Daypart's own configuration for that day of week; editing a Daypart's times retroactively updates all future scheduled events using it, and Dayparts can be shared with other users/groups ([same source]). As with Yodeck and Rise Vision, however, a Daypart in Xibo governs **which Layout is scheduled when** — it is a scheduling primitive for swapping whole layouts, not a documented mechanism for swapping a style/theme layer under otherwise-fixed content.

**Gaps relative to Theme Studio.** Xibo's Dayparting is named-and-reusable (create "Breakfast"/"Lunch"/"Dinner" once, apply across many schedules, edit centrally to cascade) which is a more structured take on "day/night variants" than the simple two-state (day/night) framing in Theme Studio's current description — an open question is whether Theme Studio's daypart concept should be an arbitrary named/reusable list (as in Xibo) or a fixed small set of built-in variants; separately, Xibo's checkout/draft/publish model keeps only one prior state, unlike Theme Studio's stated goal of multiple immutable numbered revisions, which is a difference in depth worth noting.

## 8. Toast — menu/board design tools

Toast does not appear to offer its own visual **digital menu board** theme/design tool as a native, publicly documented product feature — its digital-board story is a **data-supplier integration to a third-party board vendor (Delphi)**, not a first-party design surface. Toast's own docs state: "For customers that use a Delphi digital menu board, Toast typically recommends creating a menu specifically for display on the digital menu board... you must configure the menu correctly in Toast Web and also coordinate with your Delphi onboarding consultant," and "The Delphi digital menu board can only show prices for a published menu" ([Create a Menu for the Delphi Digital Menu Board](https://support.toasttab.com/en/article/Create-a-Menu-for-the-Delphi-Digital-Menu-Board); [Creating a menu for a Delphi digital menu board](https://doc.toasttab.com/doc/platformguide/platformCreatingAMenuForADigitalMenuBoard.html)). Toast also publishes a developer cookbook for "Building a digital menu signage integration," describing how a third party pulls Toast menu/restaurant data ("menu hierarchy, menu groups, items, modifiers, and sub-menu groups") to render on signage themselves ([Building a digital menu signage integration](https://doc.toasttab.com/doc/cookbook/apiBuildingDigitalSignage.html)) — again, Toast supplies data, not visual theming.

What Toast does have is a **Menu Builder** for its own POS/ordering menus (not a customer-facing screen theme editor): accessed via Menus > Menu management > Menu builder, it shows menus/menu groups on the left and items with images/pricing in the center, and includes a **"View POS layout"** button "which will allow you to preview the way your menus will look and function on your POS" ([search excerpt, Menu builder overview](https://doc.toasttab.com/doc/platformguide/adminMenuBuilderOverview.html); [Get Started With Menus](https://support.toasttab.com/en/article/Get-Started-With-Menus)) — a real, first-party preview feature, but scoped to the POS terminal UI rather than a digital menu board, and with no documented styling/theme layer (colors, fonts, layout templates) to speak of. Toast's separate "Building your Menu Template" article is unrelated to visual board design — it's a spreadsheet (Google Sheets/Excel) used only during onboarding to collect menu data before go-live ([Build Your Menu Template](https://support.toasttab.com/en/article/Building-your-Menu-Template)).

**Conclusion for this entry:** no native Toast menu-board theme/style editor could be verified via primary sources; Toast's own documentation instead describes (a) a POS menu builder with a layout preview, and (b) a data-integration path to third-party digital-board vendors. This is reported as a "not found" result per the task's instructions rather than filled in with assumptions.

## 9. SpotOn — menu design

SpotOn's "**Menu Screens**" feature, despite the name, is a **staff-facing POS ordering interface**, not a customer-facing digital menu board or screen theme editor: "Menu Screens are created to house all menu items and groups in one area on the SpotOn Front of House for employees to add menu items to an order," organized via a **Main Menu Screen** that links to other Menu Screens through navigable "Screen Buttons," configured from the Back of House (BOH) admin ([Menu Screens - Create Menu Screen](https://help.spoton.com/space/SK/2658075260/Menu+Screens+-+Create+Menu+Screen); [Create Main Menu Screen](https://help.spoton.com/space/SK/2658075328)). Configurable layout options found are narrow (e.g., positioning of a "Quantity Bar" as Bottom/Left/Right/Top/None), and this documentation contains no styling/theme, live-preview, or versioning features — it "applies to the selected Menu Screen and saves automatically" with no mention of drafts or history ([search excerpt](https://help.spoton.com/space/SK/2658075260/Menu+Screens+-+Create+Menu+Screen)).

A separate, closer analog to a theme editor exists for **SpotOn Order**, SpotOn's online-ordering website product: an "**Edit Theme**" screen lets a merchant set color scheme, logo, background image, favicon, and hero/menu-item images, with changes taking "effect immediately without requiring support intervention" ([search excerpt of Edit Theme - Logo, Hero Images, & Menu Item Images](https://help.spoton.com/space/SK/1976205360)). This is a website theme (colors/branding for an ordering site), not a digital signage/menu-board design surface, and the documentation found describes no preview mode or version history for it.

**Conclusion for this entry:** no native SpotOn **digital menu board** theme/design tool could be verified via primary sources. The closest documented features are (a) a POS ordering-screen layout configurator (SpotOn Restaurant BOH "Menu Screens") and (b) a basic color/logo theme editor for the separate SpotOn Order online-ordering website. Neither is a digital-signage board design tool comparable to Theme Studio's scope, and this is reported as a "not found for that specific purpose" result rather than an assumption.

## 10. Figma — Variables

**Structure.** Variables live inside named **Collections** — "A collection is a set of variables and modes" — reached from a Variables view in the left navigation, with a "+ Create variable" action to pick a type, name, and value; each collection supports "up to 5,000 variables," and variables can be organized into sub-groups (e.g., separating text colors from stroke colors) ([Create and manage variables and collections](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections)). A variable can be **scoped** "to limit which properties the variable can be applied to... reduces the guesswork when deciding which variables to use," for number/color/string types (e.g., restricting a variable to corner-radius or stroke-only usage) ([same source]). Variables can be published to team libraries for reuse across files ([same source]).

**Modes — Figma's direct analog to "variants."** Within a collection, **modes** store multiple values for the same variable, letting a design represent different contexts without duplicating frames: "variable modes allow us to represent different contexts of our designs without needing to create multiple frames for every context that we need" ([Guide to variables in Figma, search excerpt via Modes for variables](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)). Figma's own docs list exactly the kind of variant categories Theme Studio is reasoning about, generalized beyond day/night: "Light/Dark themes," "Responsive design" (device-size contexts), "Accessibility" (high-contrast or color-blind themes), and "Localization" (string variables for UI copy) ([same source]). Switching is manual and scoped: select a layer, open **Appearance**, click "Apply variable mode," and choose a mode from a collection; a page can also be set to a mode via the **Page** panel, and objects inherit their parent's mode unless overridden ([same source]).

**Live preview / proofing.** Mode switching is applied directly to real Figma layers/frames — there is no separate "preview against sample data" step; the design canvas itself re-renders with the new mode's values.

**Versioning.** Figma's file-level version history is a scheduled-checkpoint model, not tied to variables specifically: "Figma saves your work by adding checkpoints to the file's version history, recording a new checkpoint every 30 minutes," a version can be selected to preview then restored via "Restore This Version" (non-destructive — "you can still access the current version in the file's version history," and comments from all versions are preserved) ([View a file's version history, search excerpt](https://help.figma.com/hc/en-us/articles/360038006754-View-a-file-s-version-history)). Retention is plan-gated: "Users working in their Drafts or in free Starter teams can only access up to 30 days of version history, but upgrading to a paid team provides immediate access to the full version history of any existing files" ([same source]). No documentation found describes a version history specific to a variable collection independent of the file's own history.

**Time-of-day / variant scoping.** Modes are the general-purpose mechanism (see above); Figma's own examples are light/dark, device size, accessibility, and localization — not time-of-day specifically, but the same primitive would apply.

**Gaps relative to Theme Studio.** Figma's mode-inheritance model (an object inherits its parent frame's mode unless explicitly overridden) is a specific mechanic Theme Studio's day/night-variant description does not yet spell out — whether overriding a variant at a smaller scope (e.g., one section styled differently at night while the rest inherits) is possible is an open question this comparison surfaces, not a recommendation to adopt Figma's exact mechanic.

## 11. Design-tokens standard — W3C Design Tokens Community Group (DTCG) format, and Tokens Studio

**The DTCG spec itself.** The Design Tokens Format Module reached "first stable version 2025.10" on 2025-10-28, "backed by more than 40 organizations, including Adobe, Figma, Google, Microsoft, Shopify, and Salesforce" ([Design Tokens specification reaches first stable version](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)). The format is JSON-based, with tokens carrying a required `$value`, a required `$type` (e.g. color, dimension, duration, fontFamily), and optional `$description`, `$deprecated`, and `$extensions` properties ([Design Tokens Format Module 2025.10](https://www.designtokens.org/tr/drafts/format/)). The stable-release announcement lists "**Theming and multi-brand support** – manage light/dark modes, accessibility variants, and brand themes without file duplication" as a headline capability of 2025.10 ([W3C announcement, as above]) — but reading the spec text itself, this is presented as a capability the ecosystem gains rather than a dedicated `$theme`/`$mode` keyword in the format: theming/multi-brand handling is left to the `$extensions` mechanism, where "tools _MAY_ add proprietary, user-, team-, or vendor-specific data" and other tools "_MUST_ preserve any extension data they do not themselves understand" ([Design Tokens Format Module 2025.10](https://www.designtokens.org/tr/drafts/format/)). In other words: the base token file format standardizes what a single token looks like; how multiple named "themes"/"modes" of the same tokens relate to each other is not itself standardized in the base spec and is left to individual tools built on top of it. This is worth flagging as a nuance — a marketing-level claim ("theming and multi-brand support") versus what the normative spec text actually commits to (extension-based, tool-defined).

**Tokens Studio (a concrete implementation of theming on top of DTCG-style tokens).** Tokens Studio is a Figma plugin for authoring design tokens as JSON, syncable to Git ([Tokens Studio for Figma Plugin](https://www.figma.com/community/plugin/843461159747178978/tokens-studio-for-figma)). Its **Themes** feature is the concrete theming mechanism the base spec leaves undefined: "The Themes feature in Tokens Studio allow you to define combinations of Token Sets that are intended to be applied together to style design elements" ([Themes (pro)](https://docs.tokens.studio/manage-themes/themes-overview)). Practically, this composes as **Theme Groups** mapped to Figma variable **Collections** (e.g., a "Brand" group) and **Theme Options** mapped to **Modes** inside that collection (e.g., "Light"/"Dark") — "A multi-brand design system may have four or forty brands to switch between," and multiple theme dimensions can be applied concurrently ("multi-dimensional theming") — e.g., brand and light/dark simultaneously ([search excerpt, Theme Groups and Theme Options / Themes overview](https://docs.tokens.studio/manage-themes/themes-overview)). The stated payoff mirrors Figma's own modes pitch: "instead of having 2 button components, light-mode button and dark-mode button, you have a single button component that takes on the styling properties of the color mode theme that is currently active" ([search excerpt, same source]).

**Live preview / proofing.** Because Tokens Studio operates inside Figma, applying/switching a theme updates the real Figma canvas directly — same as Figma Variables above, not a separate proofing surface.

**Versioning.** Tokens Studio's versioning is explicitly Git-based rather than an in-app numbered-revision model: it "has native features to push and pull Token changes easily and version-control your design decisions using the branching feature. Syncing your Tokens with a Git provider allows you to store your Design Tokens as code files in a repository" (supporting GitHub, GitLab, and Bitbucket), and separately, "Publish versioned snapshots of your tokens to create a reliable, auditable release history" ([search excerpt, sync-provider-overview and related docs](https://docs.tokens.studio/token-storage-and-sync/sync-provider-overview)). This is a fully external, developer-facing versioning model — history lives in Git commits/branches, not in a first-party in-app history browser aimed at non-technical users.

**Time-of-day / variant scoping.** Neither the DTCG base spec nor Tokens Studio documents a time-of-day-specific concept; "modes"/"themes" in both are generic named dimensions (brand, color-scheme, density, etc.) that a tool could apply to day/night if it chose to define such a mode, but no ready-made "daypart" primitive exists in either.

**Gaps relative to Theme Studio.** The DTCG spec's choice to leave theming/multi-brand composition to tool-specific extensions (rather than standardizing it) is a structural point worth noting for anyone considering a token-based internal format for Theme Studio's own variant system — it's an open question whether Theme Studio would want to define its own "extension" for day/night the way Tokens Studio defines Theme Groups/Options, versus building something bespoke; separately, Git-branch-based versioning (Tokens Studio) versus an in-app numbered-revision browser aimed at non-developers (implied by Theme Studio's "Save and versions" screen) surfaces a distinction in audience/workflow this comparison did not resolve.

## Open questions for Theme Studio

These are neutral observations of gaps or unaddressed areas surfaced by the above research — phrased as questions, not recommendations:

1. **Granularity of "variant."** Most tools that support variant-like switching (Figma's modes, Tokens Studio's Theme Groups/Options, Xibo's named/reusable Dayparts) treat a variant as an arbitrary, user-named, potentially multi-dimensional concept (any number of brands, any number of named dayparts, combinable dimensions), rather than a fixed binary. Theme Studio's current description frames dayparts as day-vs-night. Is day/night meant to be the only variant axis, or a first instance of a more general, user-defined variant mechanism?
2. **Variant inheritance/override at sub-scopes.** Figma's modes are inherited by child layers from their parent frame unless explicitly overridden at a smaller scope. Does Theme Studio's day/night model need (or explicitly reject) the ability to override a variant at less than the whole-theme level (e.g., one section styled differently at night while the rest of the theme "inherits" the day styling)?
3. **Depth of revision history.** Several comparable tools substitute a single draft/live swap (Xibo's checkout-discard-publish, ScreenCloud's single-step discard, Shopify's draft-theme-becomes-old-live-theme) for a true numbered history, while others (Canva's 1,000-version history, Figma's 30-minute checkpoints, Tokens Studio's Git branches) offer deep, browsable history through very different mechanisms (in-app browser vs. external Git). Theme Studio's design calls for "immutable revisions, never live-edited" — what depth of history and what browsing/comparison interface is intended, and is a single "current draft vs. last published" model (as several signage-specific tools use) sufficient, or is deeper numbered history required?
4. **What "live preview" is proofing against.** The tools surveyed span a spectrum: Squarespace and Shopify preview directly against the real, live content; ScreenCloud's zone-layout preview is explicitly structural-only (no content at all); Yodeck's template preview shows the template's own canned sample, not the venue's data; Rise Vision's Virtual Display shows the real configured Schedule. Theme Studio's stated design already commits to proofing against generated sample datasets scaled to a target catalog ("fits 38 of 41 items") — none of the tools surveyed do exactly this; is there a comparable capacity/overflow-detection precedent worth examining further, or is this a genuinely novel proofing mechanic among these comparators?
5. **Review/approval gating on a saved revision.** Rise Vision's Content Publishing Approval (Content Editor drafts → Content Publisher approves before going live) and Xibo's checkout/discard/publish both interpose a review step between "someone edited this" and "this is now what plays." Theme Studio's five-screen description (Library, Editor, Dayparts and motion, Save and versions, Custom template) does not mention an approval/review gate. Is multi-person review of a theme revision before it becomes usable by the menu builder in scope at all, and if so at what point in the flow?
6. **Locking specific elements vs. locking a whole revision.** Canva, Yodeck's Branded Templates, and ScreenCloud's Canvas templates all support locking specific elements (logo, layout) while leaving others (text, images) editable by a downstream user — a finer grain than "this revision is immutable." Theme Studio's revisions are described as immutable as a whole once saved. Is there a need for partial-lock behavior (some theme properties fixed, others still adjustable downstream, e.g. by the menu builder) distinct from full immutability?
7. **Standardizing the token/variant interchange format.** The DTCG spec standardizes individual token shape but explicitly leaves multi-theme/multi-brand composition to tool-specific extensions; Tokens Studio and Figma each invented their own theme/mode composition on top of it. If Theme Studio's internal theme representation is ever meant to interoperate with external tools (e.g., importing a brand's existing Figma variables or DTCG token file), how would Theme Studio's own day/night variant concept map onto — or diverge from — that ecosystem's still-unsettled theming layer?
8. **Native support in point-of-sale/restaurant platforms.** Neither Toast nor SpotOn was found (via their own public documentation) to offer a native customer-facing digital-menu-board theme/design tool — both either delegate to a third-party board vendor (Toast + Delphi) or only theme an adjacent surface (SpotOn Order's website theme, unrelated to signage). Does this absence in adjacent restaurant-tech tooling change any assumption about where venues currently get their menu-board visuals from today, and is there anything to learn from how those vendors hand data off to third-party display tools (e.g., Toast's digital-signage integration cookbook)?
