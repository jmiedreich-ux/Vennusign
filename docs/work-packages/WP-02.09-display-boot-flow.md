# WP-02.09 — Display Boot Flow

## Objective

Load and render the minimum usable display state for a routed screen.

## Status

Complete pending review and merge.

## In Scope

- Read `screenId` from `/display/{screenId}`.
- Fetch `GET /api/display/{screenId}/content` on load.
- Render a minimal board from the existing response contract.
- Add loading, not-found, and API-error states.
- Add focused frontend tests for the boot states.

## Out of Scope

- SignalR connection or events
- Heartbeat behavior
- Final visual layouts or theme editing
- Backend contract redesign

## Acceptance Criteria

- A valid screen route fetches content once and renders the returned data.
- Loading and failure states are visible and deterministic.
- The implementation uses the existing API contract without invented fields.
- Tests cover success and failure paths.

## Required Validation

- Display tests and build
- Relevant API contract tests
- `./scripts/validate.ps1 -SkipIntegration`

## Dependencies

WP-02.08.

## Completion Evidence

- Added a display content loader using `GET /api/display/{screenId}/content`.
- Added loading, not-found, service-error, and successful board states.
- Rendered only the existing response fields: screen ID, venue ID, key, name, status, last-seen time, and layout.
- Added Node-based frontend tests for URL construction, single-fetch success, 404, server failure, and network failure.
- SignalR connection, event handling, and heartbeat behavior remain untouched.
- Full repository validation is delegated to the draft PR CI run.
