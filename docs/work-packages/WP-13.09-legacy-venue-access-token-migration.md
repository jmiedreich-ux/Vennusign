# WP-13.09 — Legacy Venue Access Token Migration

## Status

In Progress on Sequential issue #366.

## Objective

Make persisted customer sessions plus active membership the primary Venue Admin authorization path while retaining a bounded, explicitly revocable and expiring config-token compatibility window.

## Scope

- Customer-session Venue Admin authentication with server-validated organization/venue membership.
- Safe onboarding-venue default and optional server-checked venue selection.
- Membership and entitlement-derived Venue Admin claims.
- Global and per-token legacy enable/revoke/expiry/retirement controls.
- Customer-session-first bootstrap and temporary legacy fallback wording.
- Focused security/frontend tests and synchronized migration records.

## UX best-practices consultation

The dedicated UX connector remains unavailable. W3C/WAI forms, status-message, and focus guidance applies: make the preferred sign-in action primary, keep temporary recovery secondary, label fields/instructions explicitly, expose actionable authentication errors, and preserve visible keyboard focus.

## UI/function gap analysis

- Primary goals: enter with an existing customer session; otherwise authenticate; use a legacy venue link only during migration.
- Hierarchy/navigation: secure customer sign-in is primary; legacy access is a secondary disclosed compatibility form; successful entry retains existing workspace navigation.
- Data/actions: authenticate session, resolve an authorized venue, optionally submit a legacy token, sign out, and retry. Token creation/edit/delete is configuration/operations-owned and never exposed in UI.
- Essential states: checking session, customer session accepted, signed out, invalid/expired/revoked/retired legacy token, unauthorized membership, API error, and legacy compatibility success.
- Validation/destructive actions: legacy input is required only when opened; sign-out revokes the customer session when used and clears local compatibility state. No destructive customer-data action exists.
- Accessibility/responsiveness: headings, explicit instructions/labels, disclosure semantics, status/alert text, keyboard focus, and narrow-screen continuity.
- API/data/security: HttpOnly customer cookie, persisted session validation, active membership/venue ownership, entitlement-derived capabilities, constant-time legacy comparison, no raw-token persistence/logging/response.

## Acceptance criteria

- Customer session plus active authorized membership grants only its permitted venue.
- Cross-organization venue selection fails.
- Revoked, expired, disabled, or retired legacy entries fail; accepted legacy comparison stays constant time.
- Customer-session entry is primary and legacy access is clearly temporary.
- Focused affected-area validation passes; integration/provider tests remain skipped.
