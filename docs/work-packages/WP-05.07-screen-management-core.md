## Goal

Give venue administrators one responsive, venue-scoped workflow to register, identify, monitor, edit, and refresh their screens.

## Scope

- Create a venue-owned screen and issue its `/display/{screenId}` registration URL.
- List screens with deterministic ordering, status, and last-seen health.
- Rename screens and maintain optional location labels.
- Push current content to one selected screen through the existing notification abstraction.
- Enforce venue ownership for every screen read and mutation.
- Add focused non-integration repository, service, authorization, and frontend tests.

## Acceptance Criteria

1. A screen created from a venue is immediately owned by that venue and has a unique screen key.
2. Registration URLs route to the existing display boot path.
3. Health, name, location, and last-seen data are visible in a mobile-responsive list.
4. Cross-venue updates and pushes return not found and do not mutate or notify.
5. Manual push targets only the requested screen.
6. Required GitHub Actions checks pass on the reviewed head.
7. Integration-type tests remain skipped.

## Boundaries

No pairing changes, bulk or broadcast targeting, overflow visualization, video-wall configuration, display templates, theme editing, or scheduling.
