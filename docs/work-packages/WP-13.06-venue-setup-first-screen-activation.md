# WP-13.06 — Venue Setup and First-Screen Activation

## Status

In Progress on Sequential issue #360.

## Objective

Resume the entitled customer journey by creating its first organization venue and linking the first physical display through the existing pairing-code lifecycle, without confusing a saved screen record with an active online device.

## Scope

- Customer-owned initial venue creation with organization entitlement and tier venue limits.
- Name, IANA timezone, venue type, primary language, and optional secondary language inputs.
- First-display pairing-code claim bound to the onboarding venue and protected by tier screen limits.
- Durable VenueId and FirstScreenId progression in the WP-13.05 onboarding state.
- Waiting, expired, already-claimed, assigned, paired/offline, online, loading, error, success, and resumable UI states.
- Focused API/data/frontend tests and synchronized architecture/status/tracker/handoff records.

## Boundaries

The display/player continues to create its device record and six-digit code through the existing public registration path. This package claims that code for the customer-owned venue; it does not build general screen lifecycle remediation from issue #345. WP-13.07 timeline polish, WP-13.08 Super Admin visibility, WP-13.09 legacy-token migration, phase closure, and Phase 14+ are excluded.

## UX best-practices consultation

The dedicated UX connector remains unavailable, so current W3C/WAI primary guidance was consulted:

- keep forms short, explicitly labeled, and limited to information required for the task;
- provide instructions and text validation/error feedback;
- expose asynchronous waiting, error, and success changes through status/alert semantics;
- preserve visible keyboard focus;
- avoid forcing users to race a security timeout by giving an explicit fresh-code path.

## UI/function gap analysis

- Primary goals: save the first venue, understand how the physical display produces a code, claim it, and know whether the device is merely paired/offline or actually online.
- Navigation/hierarchy: continue within `/onboarding`; show one current action beneath the existing ordered progress rather than adding redundant app navigation.
- Data/actions: create and read the onboarding venue; read pairing-code validity; claim the first display; refresh device status. Venue edit/delete and general device management are intentionally deferred because they belong to operational lifecycle remediation, not initial activation.
- Essential states: loading, unauthenticated, entitlement-required, venue saved, device/code not ready, malformed/expired/already-claimed/assigned code, pairing in progress, paired/offline, online, API error, and resumable success.
- Validation: required bounded venue fields, IANA timezone selection, two-letter language codes, six-digit pairing code, server ownership/entitlement/limit checks, native constraints, and actionable text errors.
- Destructive actions: none; a failed or expired code leaves venue/onboarding progress unchanged and users request a fresh code on the display.
- Accessibility/responsiveness: explicit labels/instructions, semantic progress and forms, status/alert regions, visible focus, keyboard operation, non-color status text, and one-column narrow layout.
- API/data/security: customer-session identity only; no client user/organization/venue IDs; organization subscription authority; tier venue/screen limits; pairing and screen repositories; durable onboarding state; no entitlement from client or return parameters.

## Acceptance criteria

- Only the authenticated customer journey can create the first venue and claim its first display.
- A second venue cannot be created through the same onboarding state.
- Venue and screen limits are enforced before mutation.
- Invalid, expired, already-claimed, assigned, or missing pairing records do not advance onboarding.
- Successful claim links the device screen to the saved venue and persists FirstScreenId.
- UI text and state distinguish created/paired/offline from Online/active.
- Affected-area validation passes; integration/live-device tests remain skipped.
