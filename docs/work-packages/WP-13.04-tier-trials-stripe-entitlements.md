# WP-13.04 — Tier-Defined Trials and Stripe Entitlements

## Status
Blocked in Sequential issue #347 and draft PR #349.

## Scope
- Tier-managed no-card trial days (0–90), expiry behavior, venue limit, screen limit, public/active availability, and existing feature matrix.
- Trial creation resolves the selected tier and rejects unavailable or non-trial tiers.
- Screen creation enforces authoritative active/unexpired subscription state and tier screen capacity.
- Existing Checkout only creates a hosted Stripe session; paid activation remains webhook-authoritative.

## Boundaries
No signup/onboarding UI (WP-13.05), simulated Stripe completion, Phase 14 work, or external integration tests.

## UI/function gap analysis
No page or screen changes. Existing tier-management API accepts the added policy fields. Public plan selection, validation/states, navigation, accessibility and responsive presentation belong to WP-13.05.

## Validation
Affected-area Actions run #734 passed on implementation head `55eada08afc3e8fe7afca85a133518e341ed2512`; final completion-record head validation remains required. Integration, live Stripe, Azure SQL, hosted-infrastructure and cross-system tests were skipped.

## Material blocker

The existing authoritative subscription and Stripe metadata model is venue-scoped. Phase 13 requires authentication and tier/trial selection before venue creation, plus enforcement of a tier-defined maximum venue count. The branch can safely resolve trial duration and screen capacity, but cannot satisfy organization-level venue entitlement or Stripe customer ownership without choosing and documenting whether the authoritative commercial subscription moves to the organization or gains a separate organization entitlement linked to venue subscriptions. PR #349 must not merge until that architecture and migration/compatibility path is approved and implemented.
