# WP-13.03 — Passkeys, TOTP, and Account Recovery

## Status

In Progress — Sequential claim on issue #341 and PR #342.

## Objective

Add phishing-resistant passkey enrollment/sign-in, protected TOTP fallback, single-use recovery codes, and explicit recent-authentication/step-up rules without introducing password login.

## Scope and acceptance criteria

- Use maintained `Fido2` 4.0.1 for WebAuthn option creation and cryptographic attestation/assertion verification.
- Persist protected, five-minute, one-time, user-bound WebAuthn challenges and public-key credentials.
- Protect TOTP secrets at rest; accept a bounded clock window and reject replayed counters.
- Generate recovery codes from cryptographic randomness, persist hashes only, and consume each code atomically once.
- Record authentication assurance and step-up time on customer sessions; require recent authentication for factor enrollment.
- Preserve WP-13.01 identity boundaries, WP-13.02 OIDC/email behavior, and legacy Venue Admin authorization.
- Add migration 042, focused unit/security tests, architecture records, and exact-head Actions validation.

## Boundaries

- No public signup/onboarding UI; that belongs to WP-13.05.
- No password login, SMS factor, provider secret, or home-grown WebAuthn signature validation.
- No Phase 14 or later work.
- Integration, live-provider, Azure SQL, hosted-infrastructure, browser/device, and cross-system tests are skipped by standing instruction.

## UI/function gap analysis

No page or screen is added or changed. This package supplies authenticated APIs and persistence for later Phase 13 UI packages. Browser ceremony UX, navigation, responsive/accessibility states, validation messaging, and recovery presentation remain explicitly assigned to WP-13.05/WP-13.07; this package defines the required API, authorization, validation, one-time challenge, and destructive-consumption support.

## Dependency decision

`Fido2` 4.0.1 is used because the repository does not use ASP.NET Identity and must not implement WebAuthn cryptography itself. The dependency is confined to the API passkey adapter; domain persistence remains independent.
