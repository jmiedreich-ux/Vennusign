Deep page and function audit

Operational UI & Function Gap Analysis

Assessment of existing Vennu operational surfaces only: Super Admin, Venue Admin, display pairing/player, billing, menu, screen, theme, schedule, tap-list, and POS-management accessibility. Customer identity, public signup, no-card trials, and onboarding are intentionally excluded because they are covered by Phase 13 planning.

Purpose and method

This is a page-by-page and function-by-function audit of product surfaces that already exist. It asks whether an intended operator can complete their job without support, whether the necessary create/read/edit/delete and recovery operations exist, whether navigation is coherent, and whether UI state is backed by the necessary APIs.

Important scope boundary This report does not repeat the Phase 13 gaps for customer identity, customer signup, account recovery, tier-defined trials, or customer onboarding. Those remain Phase 13 work. Findings here identify deficiencies in the existing operational product after a user already has authorized access.

Evidence reviewed: active React route composition, page components, typed frontend API clients, API controller inventory, domain/migration inventory, and existing test inventory. It is not a substitute for hands-on usability research or a live-browser accessibility audit.

Main conclusion The codebase contains many individual operational capabilities, but several surfaces stop at the first happy path. The most common gaps are incomplete lifecycle actions, hidden or missing navigation, unsafe destructive actions, confusing state feedback, and implemented backend capability without an accessible user workflow.

The next remediation work should not begin as cosmetic UI polish. It should close task-completion gaps: an operator must be able to find a feature, understand its state, make the intended change, safely undo/recover it, and confirm the result on the relevant display or backend state.

Super Admin page audit

Dashboard

Primary job: assess commercial and fleet health, then drill into an actionable venue or screen problem.

Strong read model

Existing functions

Displays revenue snapshot/trend, venue and fleet metrics, screen-health items, and recent commercial events. It has loading and some error states.

Functional gaps

High Metrics are not actionable drill-downs. Venue counts, offline/outdated screen indicators, events, and revenue-tier information are display-only. A support operator cannot click an offline screen, a trialing venue count, or a commercial event to reach the relevant record.
High No refresh, time range, filters, or saved operational views. The dashboard loads once. There is no visible refresh action, last-updated timestamp, date-range selection, venue filter, severity filter, or “needs attention” queue.
Medium Partial failures are inconsistent. Revenue and trend failures are shown, but the events request silently becomes an empty list. An empty list can mean “no events” or “failed to load.”
Medium The “screen health map” is a list, not a navigable fleet-management map. It lacks grouping, filtering, remediation actions, and links to venue/screen detail.

Recommended outcome

Add clickable metric cards, an attention queue, refresh/last-updated data, resilient partial-error presentation, and drill-through to venue/screen support detail.

Venue Directory

Primary job: find, inspect, create, and triage venues.

Core list and create path

Existing functions

Searches venues and filters by subscription status and screen health. It shows venue/tier/status/screen count/last activity/override/health columns. It opens detail and creates a venue.

Functional gaps

High Query model supports a tier filter but the UI does not expose it. The typed query contains tier, but the directory toolbar only provides search, subscription status, and health controls.
High No pagination, sorting, saved filter, URL state, or export. As venue count grows, the list cannot reliably support operations. Browser refresh/back navigation loses directory context.
High Creation gives no operational post-create checklist. The UI creates a Starter trial and opens the detail. It does not surface provision result, screen next step, POS next step, or account/onboarding status. Phase 13 owns customer access; this finding concerns the internal operational follow-through.
Medium Empty/error states are weak. “No venues match these filters” does not distinguish first-use from restrictive filters and offers no clear reset. Load failure has no retry control.

Recommended outcome

Add tier filtering, server-backed pagination/sorting, URL-addressable filters, “needs attention” filters, retry/reset controls, and a post-provision operational checklist.

Venue Detail

Primary job: understand a venue, safely support it, and reach the right operational surface.

Incomplete support lifecycle

Existing functions

Shows basic venue profile, subscription/tier, screen limit, effective features, active feature overrides, tier switching, and override creation/removal. It includes links toward Venue Admin.

Functional gaps

Critical The API type includes screens, but the page does not render the screen list. Support staff cannot inspect individual screen status, platform, version, last-seen, pairing state, or navigate to a screen remediation action from the venue detail page.
High No venue profile edit, archive, or lifecycle action. Profile is read-only despite venue creation. There is no visible correction path for name, timezone, type, languages, status, or archive/decommission.
High Tier switching is high-impact with limited safety context. It lacks explicit plan-impact preview, feature/screen-limit conflict warning, confirmation, Stripe processing state explanation, or history.
High Feature-override removal has no confirmation or visible audit history. The page shows active overrides but only recent matrix-wide audit elsewhere; a support operator cannot see venue-specific override history, actor, or impact.
Medium Venue Admin links do not establish an operational handoff. They send the browser to a token-authenticated workspace without an authenticated support/impersonation model or clear explanation if access fails.

Recommended outcome

Render the existing screen support data, add guarded venue edit/archive flows, show tier/override impact and audit history, and create safe support handoffs rather than raw workspace links.

Tier Management

Primary job: safely define commercial catalog tiers and enforce operational limits.

Basic CRUD present

Existing functions

Create, edit, clone, archive, activate/publicly expose tiers, define price, max screens, and Stripe product/price mappings.

Functional gaps

High High-impact catalog changes have no impact preview or confirmation. Archive and clone execute immediately. Changes to Stripe IDs, price, public state, and screen limits do not explain affected venues or checkout behavior.
High There is no searchable comparison table, version/audit history, or validation status. Operators cannot quickly compare tiers or verify that public active tiers have valid monthly/annual mappings.
Medium Trial behavior is absent from this surface. Phase 13 owns tier-defined trials, but this confirms that the eventual trial policy needs a clear tier-management UI rather than hidden configuration.

Recommended outcome

Add catalog validation, dependency/impact preview, archive confirmation, change history, and a comparison-oriented tier list. Incorporate Phase 13 trial policy when that model exists.

Feature Matrix

Primary job: manage product entitlements safely across tiers.

Bulk editing exists

Existing functions

Displays features by tier, stages changes, supports save/discard, enable-all/clear-all, and displays recent audit records.

Functional gaps

Critical Enable-all and clear-all are destructive bulk actions without confirmation, scope preview, or undo. A single click can stage a matrix-wide change; the page does not show the exact impact before save.
High No search/filter or feature explanation. A growing matrix becomes difficult to manage. Feature labels/keys do not explain customer impact or dependencies.
High Limit values exist in the typed model but cannot be edited in the matrix UI. The matrix exposes enabled/disabled only, leaving a gap between entitlement representation and management controls.
Medium Audit is short and not actionable. It shows only ten recent changes with no filtering, detail, rollback, or linked affected-tier/venue impact.

Recommended outcome

Add change review/confirmation, scoped bulk operations, feature search/help, limit editing where applicable, and a searchable audit/history view.

Venue Admin page audit

Home and Settings routes

Primary job: orient the operator and manage venue-level configuration.

Placeholder routes

Evidence

The navigation exposes Home and Settings, but the route renderer returns a generic “Foundation ready” placeholder for allowed routes that are not Billing, Menu, Screens, Themes, Schedules, or Tap List.

Functional gaps

Critical Home has no operational dashboard. There is no venue health summary, screen state, current content/schedule state, urgent issue list, or direct next action.
Critical Settings has no settings management. There is no venue profile, timezone/language configuration, operational preferences, account/security links, support information, or integration entry point.
High Navigation promises functionality that does not exist. Placeholder routes create a trust problem and hide essential actions that have no other natural location.

Recommended outcome

Replace Home with a venue operations dashboard and Settings with genuine venue configuration. Do not retain visible navigation to placeholder surfaces.

Menu editor and Quick Update

Primary job: maintain an accurate, display-ready menu quickly and safely.

Important lifecycle gaps

Existing functions

Create sections/items; rename and activate/hide sections; reorder sections; edit name, description, price, happy-hour price, availability, quantity, tags, and bestseller state; set daily special; quick-toggle availability.

Functional gaps

Critical No visible delete/archive action for menu sections or menu items. A venue operator can create data and edit it, but cannot remove obsolete sections/items through the current UI.
High No menu-item reordering. Section order can change, but item order cannot. This conflicts with display presentation and overflow behavior that rely on deterministic item order.
High No menu creation/selection lifecycle. The page uses the first returned menu. If no menu exists, it only says “No menu exists”; the operator cannot create or select a menu from this surface.
High Blur-save is unsafe and ambiguous. Section/item fields persist on blur, but there is no per-row saving/saved/failed indicator, discard action, conflict handling, or retained unsaved draft after failure.
High Quick Update lacks service-safe feedback. Availability can be toggled rapidly, but there is no confirmation/undo, bulk action, filter, search, or explicit explanation of automatic midnight restoration beyond a static sentence.
Medium The item model includes more presentation data than the create form exposes. New items initially capture only name and price; description and other presentation fields require a later edit pass.
Medium No clear empty-state action hierarchy. A venue with no menu, no sections, or no items does not get guided, contextual setup actions.

Recommended outcome

Add section/item archive/delete with confirmation and undo where possible; item reorder; menu selection/creation; explicit save state; search/filter/bulk availability; and first-use empty states.

Screens and Video Walls

Primary job: create, pair, configure, monitor, replace, and retire venue displays.

Create/edit is stronger than lifecycle

Existing functions

Create a screen, claim a TV pairing code, edit name/location/layout settings, push one/all screens, open registration URL, preview layouts, inspect basic last-seen/status, view overflow, and build/remove video walls.

Functional gaps

Critical No screen unpair, archive, delete, replace, or transfer lifecycle. An operator cannot safely retire a lost/broken screen, replace a device while retaining configuration, or remove a stale screen from the fleet.
High No pairing recovery workflow. The UI accepts a TV pairing code, but has no instructions/status for expired codes, duplicate device registrations, pending pairing, reset pairing, or support escalation.
High Capacity/entitlement context is absent. “Add screen” does not show current tier limit, remaining capacity, what happens at limit, or why creation fails.
High No filter/sort/grouping for a real fleet. Screen count grows without controls for online/offline, location, layout, version, unpaired status, or last seen.
Medium Screen edits rely on blur/autosave-like behavior. Name and location save on blur; changing layout immediately calls save. There is no saved indicator, undo, or batch edit.
Medium Push actions lack clear operational result. “Content pushed” does not distinguish online receipt, queued delivery, failed delivery, or stale/offline screens.
High Video walls lack edit, validation preview, and removal protection. A wall can be created or removed, but not edited. Removing a wall has no confirmation. The UI does not explain whether screens already belong to another wall or preview final positions on a simulated display.

Recommended outcome

Implement screen lifecycle actions, entitlement context, pairing recovery, fleet filters, delivery status, and editable/confirmable video walls with position preview.

Theme builder

Primary job: design and preview consistent venue display appearance.

Strong preview foundation

Existing functions

Basic colors/fonts, swatches, advanced presets, section colors, typography/glow controls, player-backed preview, and save-to-all-screens behavior.

Functional gaps

High Global-only theme behavior is not explicit enough. The editor saves to all venue screens, but users cannot choose a target screen/group or clearly understand whether a screen-specific override is supported.
High No explicit reset/revert/version workflow. Users can alter drafts and save, but cannot restore a default, revert to last saved configuration, compare versions, or undo a bad live theme.
Medium Preview depends on a screen but selection is hidden. The code selects the first managed screen; the operator cannot choose which screen/layout/device context provides the preview.
Medium Accessibility/readability guidance is absent. Color pickers offer no contrast feedback, readability warning, or reduced-motion/legibility preview for display distance.

Recommended outcome

Clarify scope, allow preview target selection, add reset/version/undo, and include practical contrast/readability checks.

Schedules route

Primary job: control time-based display behavior without creating conflicting operational rules.

Overloaded route

The single Schedules route renders five substantial tools in sequence: Meal Periods, Happy Hour, Screen Playlist, Emergency Broadcast, and Date-Range Promotions. These tools have distinct mental models and urgency levels.

High Navigation/information hierarchy is overloaded. There is no sub-navigation, route anchor, deep link, summary, or “currently active” overview. A user must scroll through unrelated controls to reach the desired task.
High Shared precedence is not explained across schedule types. Meal periods, happy hour, promotions, playlists, and emergency broadcasts can affect display state, but the page does not expose one consolidated conflict/precedence model.

Recommended outcome

Use schedule sub-navigation or dedicated routes, summarize active/upcoming rules, expose precedence/conflicts, and retain an emergency action that is visible but protected from accidental activation.

Meal Periods

Primary job: schedule predictable venue-local display/menu/theme changes.

CRUD exists; precedence control is incomplete

Existing functions

Create, edit, enable/disable, delete, choose days/times/layout/filter/theme preset, and show detected overlaps.

Functional gaps

Critical Conflict copy says “the first listed period wins,” but no reorder/priority control is provided. The model has sortOrder, yet the screen gives no way to intentionally choose precedence. Operators can see a conflict but cannot resolve it.
High Enable/disable appears unsaved. The button patches local state while the explicit Save button remains separate. The operator can reasonably assume “Enabled/Disabled” persisted immediately even though persistence is not invoked by that control.
High Delete has no confirmation or impact explanation. Removing a period can immediately change live display behavior, but the UI does not show affected screens/rules or ask for confirmation.
Medium No visual schedule timeline or next-run preview. Time fields and masks are difficult to audit. The user cannot see the next activation in venue-local time or test a simulated date/time.

Recommended outcome

Add explicit precedence/reorder controls, persist/announce toggles correctly, confirm destructive changes, and provide a venue-local timeline with next-run and conflict preview.

Happy Hour

Primary job: configure one safe promotional availability/price window.

Basic configuration only

Existing functions

Configure start/end, days, automatic/force-on/force-off mode, enabled state, and display active status.

Functional gaps

High No schedule preview or conflict relationship. It does not show venue timezone, next start/end, affected menu items, interaction with meal periods/promotions, or what force-on/off overrides.
Medium Active-window end is formatted in browser local time. A venue-local schedule should clearly present venue-local time, especially for remote operators/support staff.
Medium No success feedback or recoverable draft. Save failure is shown, but successful persistence and last updated state are not clearly communicated.

Recommended outcome

Add venue-local next-run preview, clear override explanation, cross-schedule conflict context, and explicit save status.

Screen Playlist

Primary job: create and maintain screen-specific rotating content.

Lifecycle and scheduling gaps

Existing functions

Select a screen, add menu/image/message slides, set dwell time, optionally set a time window, reorder, and remove slides.

Functional gaps

Critical Existing slides cannot be edited or enabled/disabled. The data model exposes isEnabled, title/body/media/timing, but the current UI provides only reorder and remove for existing slides.
High Time-window day selection is a raw numeric mask. Operators are asked to enter an “Active days mask” number instead of selecting named days. This is not an acceptable operational control.
High Screen selection can remain blank after asynchronous screen load. Initial state is derived from the initial empty screen list and there is no later selection update. A user can encounter a disabled form without an explanation.
High No preview, collision handling, or active-now state. The operator cannot see which slide is live, what follows, whether windows overlap, or how media will render.
Medium Remove is immediate and there is no duplication/template action. High-frequency content management needs safer recovery and faster reuse.

Recommended outcome

Add edit/enable actions, named day controls, no-screen empty state, current/next preview, collision validation, confirmation/undo, and duplicate/template support.

Emergency Broadcast

Primary job: interrupt normal display operation quickly and safely in an emergency.

Safety-critical workflow needs hardening

Existing functions

Create all-screen or targeted broadcast with title, message, optional media URL, duration, active count, and cancel action.

Functional gaps

Critical Activation has no final confirmation, target impact summary, or preview. A single submit can interrupt all venue screens. The user should confirm target count, duration, and message before activation.
High History, delivery state, and failed-target diagnostics are absent. Only currently active broadcasts are displayed. Operators cannot see expired/cancelled history, whether a specific screen received the broadcast, or how to retry.
High No edit/extend/replace workflow. Correcting an active message requires cancellation and recreation, with no clear handoff/continuity.
Medium Cancel has no confirmation or audit context. Stopping an emergency message is also high-impact.

Recommended outcome

Use a confirmation step, explicit target/online-screen summary, history/audit, delivery diagnostics, extend/replace controls, and guarded cancellation.

Date-Range Promotions

Primary job: plan, edit, activate, and retire bounded promotional display behavior.

Basic create/edit/archive present

Existing functions

Create/edit promotion dates, target layout, title/body, priority, and archive enabled rows.

Functional gaps

High Enabled state is represented but not controllable in the form. The draft model includes isEnabled, but neither create nor edit exposes an enabled/disabled control. A user cannot safely pause a promotion without archiving it.
High No conflict/calendar preview. Priority is editable but the page does not show overlap/conflict resolution, active-now state, or venue-local calendar timeline.
Medium Archive is irreversible from the visible UI. There is no archived list, restore action, confirmation, or audit history.

Recommended outcome

Add enabled toggle, conflict and active-state preview, calendar/timeline view, archive confirmation, and restore/history lifecycle.

Tap List

Primary job: operate a brewery/bar board with current categories, availability, pricing, and order.

Most complete operational CRUD surface

Existing functions

Create/edit/delete/reorder categories and tap items; set price/style/ABV/IBU/colors/availability/coming soon; assign category; show Tap Strips capacity/overflow.

Functional gaps

High Delete actions have no confirmation or dependency warning. Deleting a category may affect linked items; the UI does not explain what will happen before executing it.
High The item model has a description field that the UI does not expose. The user cannot manage all represented tap-item data through the page.
Medium No search/filter/category grouping or display preview. A large tap list is difficult to operate, and capacity text does not show the exact display placement/overflow outcome for all supported board layouts.
Medium No bulk availability action or event feedback. Rapid service changes require more efficient operations and clear live-update confirmation.

Recommended outcome

Add dependency-aware deletion, description editing, search/filter/grouping, display preview, bulk availability controls, and stronger success/realtime feedback.

Billing

Primary job: understand current entitlement and manage paid subscription/hardware decisions.

Status is clearer than choice

Existing functions

Shows current tier/subscription status, opens Stripe Billing Portal when permitted, and presents HaaS bundles or contract summary. Feature locks can launch an upgrade modal.

Functional gaps

High No direct plan comparison or general plan-change workflow. Upgrade starts from locked features, not a clear billing catalog. The customer cannot readily compare tiers, screens, features, pricing, or choose a plan from Billing.
High No clear entitlement/limit explanation. Current tier is shown, but screen usage versus limit, feature inclusions, trial/period end impact, and downgrade consequences are not visible here.
Medium Limited recovery states. Portal unavailability is stated, but there is no clear next action for payment failure, cancellation, entitlement delay, or webhook processing beyond a generic return notice.

Recommended outcome

Add a plan comparison/selection experience, current usage and entitlement explanations, downgrade impact preview, and actionable billing recovery states. Phase 13 later connects this to customer signup/trial flow.

Display pairing and player audit

TV pairing page

Primary job: place a TV into a pairable state and communicate exactly what the venue operator must do.

Clear minimal flow

Existing functions

Registers a pairing screen, generates/refreshes a six-digit code, polls for claim, redirects when linked, and shows loading/error/ready states.

Functional gaps

High Error recovery is “reload this screen” only. The display does not provide Retry, network status, diagnostic code, last registration state, or safe reset/forget-device action.
High No pairing status explanation after the code is entered. The TV can remain waiting without telling the user whether the code was entered, rejected, expired, or claimed for another venue.
Medium No QR/deep-link assistance or accessibility fallback beyond text code. The six-digit code is accessible, but a mobile operator workflow could be faster with a QR/deep-link while retaining code fallback.
Medium No customer-visible device lifecycle guidance. There is no practical explanation for replacement, reset pairing, moving a display, or reconnecting after network changes.

Recommended outcome

Add retry/reset diagnostics, explicit pairing progress, recovery guidance, and optional QR/deep-link assistance. Keep the code as the reliable fallback.

Display player / provisioning routes

Primary job: reliably render assigned content or explain why rendering cannot continue.

Route foundation exists

Existing functions

Resolves pairing, provisioning, display, and not-found routes; supports platform bootstrap and reset-pairing query behavior.

Functional gaps

High Not-found/provision failure guidance is generic. “Use a display URL with a screen identifier” does not help an operator distinguish bad URL, revoked screen, unavailable venue, offline API, or expired provisioning token.
Medium Operational support state is not surfaced. There is no support-friendly display identifier, version, connectivity, assigned venue name, or recovery instruction on failure surfaces.

Recommended outcome

Provide non-sensitive diagnostic context, clear recovery paths, and distinct messages for URL, registration, entitlement, connectivity, and provisioning failures.

Required validation journeys for remediation

Each remediation should be tested as a complete operational task, not only by service/controller unit tests.

FindNavigate to the correct operational surface from a meaningful entry point.
UnderstandSee current state, limit, conflict, permission, and next action.
ChangeCreate/edit/reorder/archive/unpair using valid input and clear feedback.
ConfirmSee saved, queued, delivered, or failed result without ambiguity.
RecoverRetry, undo, restore, replace, or obtain safe support context.

Minimum journey cases

  • Create, reorder, hide, archive, and restore menu content; verify corresponding display state.
  • Create screen, pair TV, handle expired/invalid code, push content, unpair/replace/archive device, and verify entitlement limits.
  • Create overlapping meal periods, set precedence, preview next activation, disable/enable, and delete with confirmation.
  • Create/edit/disable/reorder/remove playlist slides with named-day scheduling and display preview.
  • Activate, confirm, deliver, replace, cancel, and audit an emergency broadcast across one and all screens.
  • Connect, import, monitor, retry, disconnect, and diagnose each supported POS provider from Venue Admin.
  • Change tier/features with impact preview, confirmation, audit, and resulting entitlement visibility.
  • Use dashboard/directory/detail drill-down to identify and resolve a degraded or offline screen.

Before implementing any affected UI surface, consult the available UX best-practices MCP and record its applicable guidance in the work package or pull request, as required by repository governance.
