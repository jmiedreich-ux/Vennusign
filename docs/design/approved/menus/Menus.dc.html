Menus — reworked

Scoped to Menus only — Today, Schedules, Screens, the rest of the routes and all mobile layouts are parked until this area is settled. Wireframed from the current source: MenuSectionsEditor, MenuItemsEditor and QuickUpdateMode. Left navigation and its colors are unchanged — the four groups, nine routes, labels and descriptions are exactly navigation.mjs, same dark ink and sky accent.

Six rules applied everywhere.

  1. One save model per surface. Live ops commit instantly with undo. Structural edits are drafts with an explicit apply. Today the same screen mixes onBlur autosave, per-row Save buttons, and draft bars.
  2. Drag to reorder. Every ↑/↓ pair in the codebase (sections, taps, categories, meal periods, playlist slides) becomes a drag handle.
  3. The TV is always visible. Screens and Themes already render real player iframes — every content surface gets one.
  4. Rows summarize; panels edit. A tap row currently has ~14 inline inputs. Rows become readable lines; editing opens one focused panel.
  5. Machine states become sentences. "Delivery: requested · revision 12 · acknowledgement pending" becomes "Bar is showing revision 12."
  6. Locked features are hidden, not disabled. Per your call — no more inline "· Pro" options, tier-prompt asides, or soft-locked fieldsets. Upgrade discovery is deferred, not designed into these screens.

Onboarding is a fullness, not a mode
Zero menus and this screen is the import flow. Three menus and it is a shelf with the same affordance in the last slot — the routes themselves are drawn in M1a. Nothing to fall out of, nothing to re-enter, and no separate wizard to maintain.
Only surface what the machine is unsure about
After any import, confirm the four rows we could not read — not the thirty-one we could. This is a product principle, not a step in a wizard: it should govern spreadsheet import, photo capture and POS sync alike.
Settled — spreadsheet import
We publish the headings and read them in any order, with only Item and Price required. A template is offered but never required, since the common file is one they already have. Extra columns are the only thing worth asking about. Drawn in M1a.
M1aImport — the four routes, drawnevery route ends in the same place: confirm only what we couldn't read

The routes differ in what they ask you for — a photo, a paste, a file, a connection. They do not differ in what happens next. All four produce the same thing: a draft menu, plus a short list of rows the machine wasn't sure about. Nobody proofreads thirty-one correct rows to find four wrong ones (decision 18), and nothing reaches a screen — an import lands on the shelf as a draft like any other new menu.

One section / whole board is a zoom, not a mode
It sits on the canvas as a pill pair, deliberately unlike the header's Quick update / Build switch — that one changes surface and commit model, this one only changes how far away you are standing. Click into a block and you are back at M2 with that section open.
Pages are a consequence, not a setting
Nobody chooses "5 pages." Page 4 exists because Wine overflowed, and it's drawn dashed to say so. Fix the overflow and it disappears — which is why the page strip has to be visible while you arrange.
Adapt first, override where it breaks
One layout per board, reflowed to each screen's reported geometry, with a per-screen override only where the automatic result is wrong. Per-screen layouts everywhere would double the work and the concepts — same principle as the geometry correction in M2c.
Still to settle
Whether zones are a fixed set the theme provides (full width, two columns, sidebar) or free-form. Fixed keeps boards looking designed and makes reflow tractable; free-form makes every screen a bespoke layout problem. I'd take fixed.
M2cPlay — walking the boardnot a preview of your edit; the real cycle, at real scale, on every screen

There is no Preview button, because M2's canvas already is the preview — adding one would imply the thing you're editing isn't real. What the canvas can't answer is the question you ask before a shift: does the whole board work? It shows one section, at editing scale, on one screen. Play takes over the canvas and runs the actual cycle — real page breaks, real dwell times, real screen sizes — as a thing you watch, not edit.

Where it lives
A ▶ Play control in M2's header, beside the screen picker. Not a modal you dismiss — it takes the canvas and gives it back, so you can play, spot the split, close, fix, play again.
It plays your draft
Including the 3 unpublished changes, clearly labelled. Playing the live board instead would make it useless for the thing you'd use it for — checking work before it ships.
The screen reports; Play never dictates
Geometry comes from the device on pairing and on every reconnect — resolution, orientation, safe area, panel size. The tabs are the screens you own, not aspect-ratio options. Lobby is offline but still renders from its last report — that geometry doesn't change when the Wi-Fi drops. A screen you have not paired yet cannot be previewed against at all — there is no such thing as a representative size, only real ones.
The one thing you do send
A correction, when the report is wrong — a TV in a cabinet cropping edges, a device lying about overscan. That is a per-screen override set once under Screens, never a picker in the player. Otherwise the wrong geometry silently follows you into every board you design.

M2's header changes meaning to match: it is no longer "pick an aspect ratio," it is "show me this board as Bar / Patio / Lobby." An operator should never have to know their own screen's resolution — and should never be able to get it wrong. Play is read-only by design. The moment you can edit inside it, it becomes a second editor with a different layout — which is how the old build ended up with two of everything.
